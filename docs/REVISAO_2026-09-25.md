# Revisão acompanhável — 25/09/2026

## Resultado e alcance

O responsável confirmou que o deploy com inicializador customizado resolveu o login e a comunicação com MySQL. Esta revisão trata o erro de `filter` nos chamados, verifica a refatoração já existente e revisa segurança. As alterações desta revisão estão locais: não foi feito commit, push ou deploy.

## Entendendo o erro da tela

O painel técnico consulta chamados a cada 10 segundos. `response.data` no Axios é o corpo HTTP; o segundo `.data` é o campo da lista dentro desse corpo. O TypeScript descrevia o que se esperava receber, mas não conferia o que chegou pela rede. Se viesse `{ message: "..." }` ou HTML em uma resposta de sucesso, a leitura da lista poderia produzir undefined; a renderização seguinte tentava chamar filter.

Agora a resposta passa por validação antes do setState. Lista vazia válida continua sendo `[]`; resposta inválida lança um erro controlado. No painel de chamados, a última lista válida permanece e surge aviso de possível desatualização; uma resposta válida posterior remove o aviso. O conteúdo exato da resposta que originou o incidente em produção não foi capturado, portanto não se atribui a causa a queda do banco, expiração de sessão ou Hostinger sem evidência.

## Arquivos centrais e motivo de cada alteração

| Arquivo | Alteração | Motivo |
|---|---|---|
| `src/utils/apiResponse.ts` | Erro próprio e validadores JSON/lista/paginação | Centralizar a proteção de fronteira HTTP. |
| `src/services/api.ts` | Rejeita HTML, null e respostas incompatíveis com JSON; preserva 204/205 e downloads explícitos | Evitar que uma página de erro entre no estado como dados. |
| `src/services/chamadoResponse.ts` | Schemas Zod para itens e respostas | Proteger listas, conversas, notificações e retornos de mutações. |
| `src/services/chamadoService.ts` | Usa os schemas e o tratamento de erro comum | Validar antes de resolver a Promise que alimenta as telas. Inclui evento criado nas notificações, já emitido pela API. |
| `src/hooks/useCrud.ts` | Valida paginação e mantém lista em falha; ignora resposta atrasada | Proteger os oito cadastros que reutilizam o hook. |
| `src/services/caAprendizService.ts`, `ocorrenciaTipoService.ts` | Validação do envelope paginado nas consultas | Proteger listagens de aprendizes e tipos de ocorrência. |
| 27 páginas de acessos/cadastros/empresa/pedagógico/estatísticas | validateArray nas atribuições diretas identificadas | Impedir estado de lista indefinido ou objeto onde se espera array. |
| `src/app/chamados/admin/dashboard/page.tsx` | Aviso persistente de atualização pendente | Não apresentar dados antigos como se a atualização tivesse funcionado. |
| `src/utils/apiError.ts` | Mensagens somente se forem texto, reutilizadas em chamados | Remover duplicação e evitar renderizar objeto como mensagem. |
| `src/app/api/auth/login/route.ts` | Verifica JSON e campos da resposta antes do cookie | Resposta inválida passa a resultar em 502 controlado, sem sessão falsa. |
| `src/app/error.tsx` | Texto neutro | Não atribuir todo erro a atualização/deploy. |
| `apps/api/src/lib/sessionClaims.ts`, `server.ts` | Exige claims de sessão após validar assinatura JWT | Rejeitar tokens de recuperação como sessões e perfis inválidos. Reutiliza normalização de perfis já existente. |
| `tests/response-validation.test.ts` | Regressões de resposta e sessão | Provar aceitação de respostas legítimas e rejeição das inválidas. |
| `package.json` | npm run test:regression | Um comando reproduzível para acompanhar a revisão. |
| `scripts/generate-code-map.mjs` | Inventário reproduzível | Manter o mapa MD atualizado sem incluir segredos ou dependências. |

Não foram alterados schema do banco, dados, variáveis de ambiente ou configuração da Hostinger. A revisão não tenta validar cada campo de todos os módulos: chamados tem validação de itens; os demais pontos migrados têm checagem estrutural. Formulários com formatos especializados ainda precisam de schemas próprios. Algumas telas legadas mantêm comportamento de limpar a lista no catch; preservar a última lista foi aplicado explicitamente em chamados e useCrud.

## Testes executados

- Seis testes automatizados aprovados: JSON/HTML, lista/paginação, itens de chamados, sequência de polling inválido/recuperação, claims de sessão e resposta do proxy de login.
- TypeScript sem emissão no front e na API: aprovado.
- ESLint de src e tests com --quiet: aprovado, sem erros; avisos legados não foram tratados como falha nem apresentados como corrigidos.
- npm audit nos dois pacotes: zero vulnerabilidades conhecidas no momento da consulta.
- Build de produção do Next em cópia temporária sem .env e compilação TypeScript da API: aprovados. Prisma usou o cliente já gerado; schema não foi alterado nem foi necessário regenerar o DLL usado pelo ambiente local.
- Inicializador real na cópia temporária: /login e /api/proxy/health HTTP 200; token de recuperação assinado e assinatura adulterada HTTP 401; sessão técnica em /users HTTP 403; login vazio HTTP 400. Banco apontado para endereço inválido de teste; nenhuma autenticação real ou consulta a dados foi necessária.
- Compatibilidade funcional de todos os perfis e fluxos exige homologação após deploy. A auditoria não é um pentest completo.

## Como revisar no VS Code

1. Abra Source Control e leia primeiro apiResponse.ts, chamadoResponse.ts e chamadoService.ts.
2. Confira useCrud e o aviso no dashboard. As mudanças nas 27 páginas são pequenas chamadas ao mesmo validador.
3. Confira sessionClaims.ts e as duas chamadas em server.ts separadamente: são a mudança de segurança.
4. Execute `npm run test:regression`; depois `npm run build:all` quando o ambiente não estiver disputando .next ou o DLL do Prisma com o servidor de desenvolvimento.
5. Após revisar, publique todos os arquivos novos e alterados. Em produção, confira login, lista vazia legítima, atualização automática e permissões dos perfis.
